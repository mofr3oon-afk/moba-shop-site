# نظام شحن PUBG — نسخة تجربة معزولة

هذه إضافة برمجية فعلية للمشروع الحالي، على فرع `feature/pubg-auto-topup-simulation`.
**لا تنشر على Production، ولا تغير Webhook، ولا تستخدم أموالًا أو أكوادًا حقيقية قبل الموافقة.**

## ما يعمل بالفعل

- شراء 60 UC من البوت: ID ← فحص الاسم ← تأكيد اللاعب ← سعر محفوظ للطلب ← فودافون كاش ← محفظة المحوّل ← رقم طلب فريد ← انتظار الدفع.
- قاعدة SQLite دائمة، WAL، معاملات `BEGIN IMMEDIATE`، وقيد فريد على مرجع التحويل وحجز الكود.
- مخزون AES-256-GCM مع AAD وبصمة HMAC مستقلة لاكتشاف الأكواد المكررة.
- استيراد كود أو آلاف الأكواد من نص أو TXT/CSV، وتسجيل التكلفة لكل كود.
- لوحة Telegram خاصة بـ`TOPUP_ADMIN_IDS`: الطلبات، المخزون، الاستيراد، السعر، إيقاف البيع، التقارير، الأخطاء، حد المخزون، ووضع التشغيل.
- محاكاة كاملة للدفع والاسترداد؛ الأكواد المقبولة في المحاكاة تبدأ بـ`SIM-` فقط.
- Webhook للـSMS بتوقيع HMAC-SHA256 على الـbody الأصلي + المسار + الوقت + nonce محفوظ في قاعدة البيانات.
- مطابقة المبلغ ورقم المحوّل والنافذة الزمنية ومحفظة المستلم؛ المطابقات الملتبسة للمراجعة.
- طوابير Inbox/Jobs/Outbox دائمة. لا تُعاد مهمة تفعيل بدأت ثم انقطع السيرفر؛ تصبح `unknown` والكود `quarantined`.
- نسخة احتياطية مشفرة كل 24 ساعة أثناء تشغيل الخدمة، وأداة استعادة لا تستبدل قاعدة موجودة.
- فحص الاسم وزر نسخه الحاليان وأوامر إدارة الموقع القديمة باقيان؛ الإضافة مغلقة افتراضيًا.

## الحدود الحقيقية — قبل أي تشغيل بأموال

التفعيل الآلي الحقيقي **غير متصل**. `ManualReviewRedeemer` لا يرسل أي طلب Midasbuy، ولا يعلن نجاحًا، ولا يعيد الكود للمخزون. حتى مع تأكيد مسؤول لدفع حقيقي، الطلب يتوقف في `manual_review` والكود محفوظ للحالة نفسها. لا توجد وظيفة تُخرج الكود الحقيقي تلقائيًا إلى العميل، أو تفك حجز نتيجة حقيقية مجهولة.

هذه مراجعة آمنة للطلبات وليست ادعاء بوجود بديل يدوي متكامل للاسترداد. أي إثبات استرداد حقيقي أو كشف حالة كود يحتاج تكامل مزود مصرح به وتجربة Sandbox. `resolveSimulation()` للمحاكاة فقط؛ لا يصلح لتبرير استهلاك كود حقيقي.

SMS لا تؤكد الدفع نهائيًا، حتى لو توقيعها صحيح ومرسلها VF-CASH. لا يوجد حاليًا اتصال رسمي يستعلم عن التحويلات الواردة لمحفظتك الشخصية. طريقة التحقق الحقيقية المتاحة في الكود هي تسجيل مسؤول مخوّل أنه طابق مرجعًا ومبلغًا ورقمًا مع كشف مستقل موثوق، مع إغلاقها افتراضيًا. مصدر الدفع الرسمي المستقبلي يجب أن يستعلم من المزود ويتحقق من رد موقع، لا أن يثق بمتغير `trusted` مرسل من العميل.

النظام يبدأ ببيع متوقف ووضع Simulation. السعر الافتراضي 50 جنيه والتكلفة 40 جنيه **بيانات تجربة فقط**، وليسا أسعارًا أو أرباحًا حقيقية. التشغيل الحقيقي يتطلب ضبط سعر صريح ومحفظة المستلم وفتح بوابات البيئة؛ لا يحوّل ذلك التفعيل الوهمي إلى تفعيل حقيقي.

## تجربة محلية بدون حسابات أو فلوس

يلزم Node.js 24 (بسبب `node:sqlite`). لا توجد مكتبات NPM إضافية.

```powershell
node --test
node topup/simulate.js
```

`simulate.js` يجري خمس عمليات شراء افتراضية بالكامل داخل الذاكرة ويعرض خمس نتائج وملخص المبيعات والتكلفة. الاختبارات تستخدم أيضًا ملفات SQLite حقيقية، عاملين منفصلين يتنافسان على كود واحد، وعملية تنتهي فجأة بعد تسجيل بدء التنفيذ.

## ملفات الإعداد

راجع `.env.topup.example`. الملف مثال، ولا يتم تحميله تلقائيًا. ضع القيم في بيئة التشغيل أو Secret Manager، وليس في Git. المطلوب:

| المتغير | الاستخدام |
|---|---|
| `TOPUP_DB_PATH` | `/data/topup.sqlite` على Railway Volume |
| `TOPUP_ADMIN_IDS` | Telegram User ID أو قائمة IDs، وليس اسم المستخدم |
| `BOT_TOKEN` | توكن البوت الحالي، داخل Railway فقط |
| `STOCK_KEYS_JSON` | خريطة إصدارات مفاتيح تشفير، كل مفتاح 32 بايت بصيغة Base64 |
| `STOCK_ACTIVE_KEY_ID` | الإصدار المستخدم لتشفير البيانات الجديدة، مثل `v1` |
| `STOCK_FINGERPRINT_KEY` | سر مستقل لا يقل عن 32 حرفًا، ثابت طوال عمر المخزون |
| `BACKUP_KEY_BASE64` | مفتاح آخر 32 بايت لتشفير النسخ الاحتياطية |
| `BACKUP_DIRECTORY` | الافتراضي `/data/backups` بجوار قاعدة البيانات |
| `TOPUP_BRIDGE_SECRET` | سر HMAC مشترك بين Vercel وخدمة الشحن |
| `SMS_WEBHOOK_SECRET` | سر HMAC آخر مختلف يخص جهاز الرسائل فقط |
| `ALLOW_MANUAL_VERIFIED_PAYMENTS` | `false` افتراضيًا، لا يُفتح إلا بعد الموافقة |
| `ALLOW_REAL_STOCK_IMPORT` | `false` افتراضيًا، لحماية المحاكاة من مخزون حقيقي |
| `VODAFONE_RECEIVER_WALLET` | محفظة الاستلام المعتمدة؛ لا حاجة لها في محاكاة الشراء |

استخدم مولد أسرار موثوقًا خارج السجلات. لا تفقد مفاتيح المخزون أو البصمة أو النسخ الاحتياطية. تدوير مفاتيح التشفير يعني إضافة إصدار جديد والاحتفاظ بالإصدارات القديمة حتى إعادة تشفير بياناتها، ولا يعني استبدال المفتاح القديم عشوائيًا. تغيير مفتاح البصمة بلا ترحيل يلغي ضمان اكتشاف التكرار. لا تحتوي النسخة الاحتياطية على مفاتيح فكها.

## واجهة Telegram

الخدمة الجديدة لا تضبط `setWebhook` ولا تبدأ Polling، لتجنب إيقاف البوت الحالي. نقطة Telegram الحالية على Vercel تظل المسؤولة عن التحقق من سر Telegram.

بعد الموافقة ونشر خدمة جديدة واختبارها، يضبط مسؤول النشر **في Vercel**:

```text
TOPUP_ENABLED=true
TOPUP_SERVICE_URL=https://YOUR_SERVICE.up.railway.app
TOPUP_BRIDGE_SECRET=THE_SAME_RAILWAY_SECRET
```

قبل ذلك `TOPUP_ENABLED=false` أو غائب؛ لا يوجد أي أثر على البوت الحالي. عند التفعيل، البوابة ترسل التحديث إلى الخدمة بتوقيع داخلي؛ التحديثات غير التابعة للبيع ترجع للمنطق الحالي. زر فحص الاسم والأمر `/pubg ID` يظلان متاحين حتى عند تعطل خدمة الشحن، بينما الطلبات المالية لا تتجاوز عطل الخدمة.

أرسل `/shopadmin` في الخاص من User ID المخوّل. افتح البيع التجريبي، واضبط السعر، واستورد أكواد `SIM-`، ثم جرّب زر «🛒 شحن 60 UC». صفحة الطلبات التجريبية تحتوي زر «محاكاة دفع صحيح». المستلم يرى بوضوح أنه اختبار وممنوع تحويل فلوس.

الإدارة الإضافية:

```text
/shop_verify ORDER_REFERENCE BANK_REFERENCE AMOUNT_EGP SENDER_PHONE
/shop_requeue ORDER_REFERENCE
```

الأول مقفول افتراضيًا؛ يعني أن المسؤول تحقق من **كشف مستقل**، ولا يجوز استخدامه بناءً على SMS أو سكرين فقط. الثاني يعيد فحص المخزون لطلب `paid_out_of_stock` فقط، ولا يعيد مهمة فشلت أو أصبحت مجهولة.

رفع الأكواد يحتاج خطوة «إضافة أكواد» ثم نص أو مستند TXT/CSV. صيغة CSV:

```csv
code,cost_egp
SIM-DEMO-001,40.00
SIM-DEMO-002,39.50
```

المستند يُحمّل من Telegram الرسمي فقط وبحد 256KB، ولا تُعاد الأكواد في رسائل التأكيد. الرسائل الواردة التي تحمل الأكواد تحفظ مشفرة في Inbox. تظل نسختك المرسلة داخل محادثة Telegram نفسها؛ لا تستخدم مجموعات أو IDs غير خاصة للإدارة.

## SMS Forwarder: عقد البيانات وليس إيصالًا مصرفيًا

**الشريحة الشخصية تحتاج هاتفًا/جهازًا شغالًا ومتصلًا بالإنترنت لاستقبال ورفع SMS**، حتى لو البوت على سيرفر 24 ساعة. لا توفر الاستضافة وسيلة لاستقبال رسائل الشريحة وحدها.

`sms-edge.js` نموذج تحويل يُشغّل على الهاتف قبل الإرسال. يقبل قالب استلام محددًا فقط ويرفض OTP وPIN والكلمات السرية والرسائل الشخصية. قوالب فودافون الفعلية تختلف؛ لم يتم اختبار رسالة حقيقية من شريحتك بعد. لا تفعل تطبيق Forwarder يرسل كل النصوص. التطبيق المطلوب يجب أن يدعم ترشيحًا على الجهاز وتوقيع HMAC؛ التطبيق الذي يدعم رابطًا فقط أو مفتاحًا في Query غير كافٍ لهذا التنفيذ.

المسموح إلى `POST /hooks/sms` هو JSON من هذا النوع، وليس `message` أو `body` أو Cookies:

```json
{
  "event_id":"DEVICE_GENERATED_UNIQUE_ID",
  "observed_sender":"VF-CASH",
  "recipient":"01000000000",
  "sender_phone":"01000000001",
  "amount_minor":5000,
  "currency":"EGP",
  "occurred_at":"2026-10-17T12:00:00.000Z",
  "reference":"EXAMPLE-BANK-REFERENCE"
}
```

مرجع التحويل اختياري (`null`)، لكن غيابه يمنع الاعتماد عليه كمرجع مصرفي فريد. البصمة المحلية تكتشف الرسالة المتطابقة، ولا تثبت أن إشعارين مختلفين يمثلان تحويلين حقيقيين. كل النتائج للمراجعة فقط.

ترويسات المصادقة:

```text
x-shop-timestamp: Unix milliseconds
x-shop-nonce: random unique 16..100 alphanumeric/_/- characters
x-shop-signature: HMAC-SHA256 in lowercase hex
```

النص الموقّع بالضبط، دون تعديل JSON بعد التوقيع:

```text
POST\n/hooks/sms\nTIMESTAMP\nNONCE\nEXACT_RAW_JSON
```

استخدم `signEnvelope()` على الجهاز. لا تنقل `SMS_WEBHOOK_SECRET` إلى خدمات وسيطة مجهولة. نافذة الوقت خمس دقائق، والـnonce يستخدم مرة واحدة محفوظة في SQLite. إعادة إرسال نفس حدث صالح تحتاج nonce جديدًا لكن حدث الدفع نفسه لا يعاد احتسابه.

## دورة التنفيذ وضمان عدم التكرار

```text
player_confirmation → awaiting_wallet → awaiting_payment
SMS → payment_review (لا حجز ولا تسليم)
إثبات موثوق/افتراضي → queued (حجز ذري) → fulfilling
  نجاح موثوق في Simulation → completed + used
  رفض مؤكد بعدم الاستهلاك → fulfillment_failed + available
  خطأ/Timeout/انقطاع → unknown + quarantined
  وضع حقيقي بلا مزود معتمد → manual_review + reserved
مخزون فارغ بعد الدفع → paid_out_of_stock
```

الحجز 15 دقيقة للبدء. انتهاء الحجز لا يحرر الكود تلقائيًا؛ الطلب للمراجعة. لا يوجد تسليم كود قبل إثبات الدفع. لا توجد محاولة آلية جديدة لنتيجة مجهولة. إعادة التشغيل تعيد الرسائل المعلقة فقط، وتوقف مهام التفعيل غير المحسومة. Inbox معرّف بـ`update_id`، والتحويل له قيد فريد لكل وضع، ومعرّف مهمة التفعيل ثابت.

لا يمكن ضمان exactly-once لرسائل Telegram عبر انقطاع اتصال بعد الإرسال وقبل تسجيل الرد؛ Outbox يعيد إشعارًا آمنًا قد يتكرر، لكنه لا يعيد تفعيلًا ولا يحمل كود شحن. التفعيل الحقيقي نفسه لا يبدأ في هذه النسخة.

## النشر المقترح: Railway للخدمة، Vercel للموقع

اختر Railway لهذه الخدمة لأنه يشغّل Worker دائمًا مع قرص دائم، واترك الموقع الحالي وSupabase على Vercel. SQLite مناسبة لهذه البداية **بخدمة واحدة وReplica واحدة وVolume واحد**. عند الحاجة لتوسعة أفقية يلزم ترحيلها إلى PostgreSQL مع قفل صفوف؛ لا تشغل نسختين من Worker على نفس القاعدة. قد يوجد انقطاع قصير أثناء إعادة نشر خدمة Railway ذات Volume.

ملفات النشر جاهزة: `topup/Dockerfile` و`topup/railway.json`. لم يتم بناء صورة Docker محليًا لأن Docker غير مثبت في بيئة العمل؛ الكود اختبر على Node 24 وSQLite الفعلية. لم يتم إنشاء استضافة أو تحمل تكلفة. تشغيل 24 ساعة يعتمد على حسابك والخطة وإلغاء نوم الخدمة، وليس وعدًا بأن ذلك مجاني.

بعد الموافقة:

1. أنشئ **خدمة جديدة** من نفس المستودع على Railway، Root Directory هو جذر المستودع، وConfig File هو `topup/railway.json`، وفرع تجربة منفصل أولًا.
2. اربط Volume عند `/data` واضبط المتغيرات المطلوبة. Replica واحدة، وإيقاف App Sleeping.
3. افحص `/health`: يجب أن يعرض `liveRedemption:false`، واختبر Simulation ببوت اختبار منفصل أولًا.
4. لا تستبدل Telegram Webhook. فعّل بوابة Vercel بالمتغيرات المذكورة بعد موافقة ربط البوت الفعلي.
5. عيّن تنبيهات فشل الخدمة ومساحة القرص. راجع مصاريف Railway بنفسك قبل الاشتراك.

## النسخ الاحتياطي والاستعادة

الخدمة تنشئ Snapshot عبر SQLite Backup API، ثم تشفر **الملف كاملًا** بمفتاح مستقل. التشغيل يدويًا:

```powershell
node topup/backup.js create /data/backups/manual-unique-name.bak
node topup/backup.js restore /data/backups/manual-unique-name.bak /data/restored-new.sqlite
```

الاستعادة لا تكتب فوق قاعدة موجودة وتفحص `integrity_check`. أوقف الخدمة قبل تبديل `TOPUP_DB_PATH` إلى النسخة المستعادة، واحتفظ بالقاعدة القديمة للمراجعة. بعد استعادة أقدم من آخر تفعيل، لا تعاود التشغيل الحقيقي قبل مطابقة سجل المزود؛ النسخة القديمة وحدها قد لا تعرف أن كودًا استُهلك لاحقًا.

فعّل نسخ Railway اليومية/الأسبوعية للـVolume، وانقل نسخة `.bak` مشفرة إلى مخزن مستقل مملوك لك بعد توفير بياناته وموافقتك. النسخ داخل نفس Volume تحمي من أخطاء التطبيق ولا تكفي لفقدان الـVolume كله. لم نربط مخزنًا خارجيًا أو نطلب أي صلاحيات غير متاحة. لا يوجد حذف تلقائي للنسخ؛ راقب السعة وحدد سياسة احتفاظ قبل التشغيل التجاري.

## المطلوب لاحقًا

- Telegram User ID للإدارة في بيئة آمنة، وحساب Railway وVolume وأسرار مولّدة ومفاتيح محفوظة خارج المستودع.
- سعر بيعك وتكلفتك ومحفظة الاستلام؛ لا تستخدم أسعار Simulation افتراضيًا في الواقع.
- عينة SMS منزوعة أي OTP/PIN/بيانات شخصية زائدة لمراجعة القالب، وتطبيق هاتف مناسب للتوقيع والترشيح.
- تكامل دفع رسمي/حساب تاجر إذا أردت التسليم الآلي الموثوق بدل المراجعة اليدوية.
- اتفاق/تكامل Midasbuy مصرح به وبيئة اختبار منفصلة قبل كتابة أو تشغيل مسترد حقيقي.
- موافقة صريحة قبل أي نشر إنتاج أو استخدام كود/أموال حقيقية.
